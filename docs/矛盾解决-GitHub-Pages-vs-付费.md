# 「GitHub Pages vs 付费」矛盾解决 spec

> **主理人**：岳上线
> **状态**：Gate G0 内部循环（矛盾识别 + 方案设计）
> **目的**：在用户拍板前，把矛盾彻底拆解清楚，给 4 个候选方案 + 1 个推荐

---

## 0. 矛盾复盘

### 0.1 用户的累计选择

| 阶段 | 选择 |
|---|---|
| Phase 0（站点诊断） | 工具落地页 / 下载试用 / 加联系表单+用户系统+AI 增强 / **GitHub Pages** |
| 付费模式设计 | 6 角色 / 4 档订阅 / 微信支付 / 14 天试用 / 多端同步 / AI 配额 |

### 0.2 矛盾的根因

**GitHub Pages 是纯静态托管**，仅能服务 `.html` / `.css` / `.js` / 图片。
**付费模式必须的能力**：

| 能力 | 服务端依赖 | 影响 |
|---|---|---|
| 微信支付回调 | **必须服务端** | 无法接收支付结果、无法激活会员 |
| 订单管理 | **必须服务端** | 不知道谁付了钱、付了多少 |
| 用户鉴权 | **必须服务端** | 无法识别登录用户、无法跨设备同步 |
| 订阅状态 | **必须服务端** | 无法判断用户当前是试用/付费/过期 |
| AI 配额限制 | **必须服务端** | 否则可绕过本地限制滥用 AI |
| 联系表单 | 第三方可代收 | Formspree 已解决 |
| AI 客户端调用 | **可纯客户端** | 用户自带 API key，无需服务端中转 |
| 工具本身 | **可纯前端** | 已有 `index.html`（单文件） |

**结论**：8 项能力中 5 项**必须服务端**。GitHub Pages 无法承载。

## 1. 需求服务端依赖性深度分析

### 1.1 必须服务端的能力（5 项）

#### A. 微信支付
**原因**：
- 微信支付商户号需要**服务端**发起统一下单 API（前端不能直接调）
- 支付完成后**异步回调**必须服务端接收并验证签名
- 订单状态、用户-订单关联都需要服务端持久化
- 前端不能"伪造"已支付

**绕过难度**：极难（涉及签名验证、商户密钥管理）

#### B. 用户鉴权与多端同步
**原因**：
- 用户注册、登录、Session 管理必须服务端
- 多端同步需要"服务器作为中介"协调冲突
- 数据上传/下载的权限校验只能服务端做

**绕过难度**：极难（这是软件工程的根本问题）

#### C. 订阅状态管理
**原因**：
- 知道用户当前是"试用 / 基础 / 高级 / AI / 过期"必须服务端
- 续费、取消、宽限期逻辑必须有后端事务
- 客户端存的状态可被篡改

**绕过难度**：高（前端数据可被 localStorage 改写）

#### D. AI 调用配额限制
**原因**：
- 防止试用用户刷调用，必须服务端计数
- 即使 AI 是客户端调用，配额校验仍要服务端

**绕过难度**：低（可不限制，但商业上不可行）

#### E. 订单与发票管理
**原因**：
- 财务数据必须服务端持久化、不可丢失
- 发票 PDF 生成、发送依赖服务端

**绕过难度**：高

### 1.2 可纯客户端化的能力（3 项）

| 能力 | 客户端化方案 |
|---|---|
| **AI 增强** | 用户自带 API key，前端直调 LLM，调用记录在本地 |
| **联系表单** | Formspree.io 第三方代收 |
| **工具本身** | 已有 `index.html`，无服务端依赖 |

### 1.3 客户端化的局限

- AI 配额只能在本地计数（用户可绕过）—— **接受"商业损失风险"或 "提升信任成本"**
- 联系表单走第三方——**已有解**
- 工具本身——**已有解**

## 2. 候选方案对比（4 选 1）

### 方案 A · 整体迁移到 Vercel / Netlify

**做法**：把整个站迁出 GitHub Pages，部署到支持 Serverless 的平台。

| 维度 | 评估 |
|---|---|
| **架构形态** | 单一平台，统一部署 |
| **服务端能力** | Edge Functions（Node.js / Go）够用 |
| **数据库** | 需额外接 Supabase / Neon / PlanetScale |
| **国内访问速度** | 较慢（海外节点） |
| **成本** | Hobby 免费额度够 MVP，Pro $20/月起 |
| **运维复杂度** | 低（一站式） |
| **数据合规** | 数据出境风险（用户可能顾虑） |
| **GitHub Pages 优势** | 失去（但 Git 部署仍保留） |
| **扩展性** | 强（Edge Functions 可支撑完整 SaaS） |
| **风险** | 国内访问慢、备案要求看情况 |

**适合**：海外用户为主 / 不在意国内速度 / 想要一站式

---

### 方案 B · 拆分部署（GitHub Pages + BFF 独立部署）

**做法**：主站放 GitHub Pages；用户/订单/支付/同步能力部署到独立 BFF（Backend for Frontend）。

```
┌──────────────────────────────────────┐
│ 主站（GitHub Pages，静态）            │
│ - 首页 / 功能 / 架构 / 下载 / 隐私   │
│ - 工具本体（index.html）              │
│ - AI 客户端调用（自带 key）           │
│ - 联系表单（Formspree 嵌入）         │
└────────────┬─────────────────────────┘
             │ HTTPS API
             ▼
┌──────────────────────────────────────┐
│ BFF（独立部署，国内云函数）            │
│ - 用户注册/登录/鉴权                  │
│ - 微信支付下单/回调                   │
│ - 订单管理                           │
│ - 订阅状态机                          │
│ - AI 配额计数（可选）                 │
│ - 数据同步端点                        │
└──────────────────────────────────────┘
```

| 维度 | 评估 |
|---|---|
| **架构形态** | 双平台（GitHub + 国内云） |
| **服务端能力** | CloudBase / EdgeOne Pages Edge Functions |
| **数据库** | CloudBase NoSQL / MySQL |
| **国内访问速度** | 主站 GitHub 慢 / BFF 快 |
| **成本** | GitHub 免费 / CloudBase 按量付费（很便宜） |
| **运维复杂度** | 中（两套部署，需协调） |
| **数据合规** | 国内云符合 |
| **扩展性** | 强（每侧独立扩展） |
| **风险** | 跨域、跨域认证、两套 CI/CD |

**适合**：国内用户为主 / 重视数据合规 / 接受运维复杂度

---

### 方案 C · 第三方代收（虎皮椒支付 / Payjs）

**做法**：用第三方支付平台代替自建支付系统。

| 维度 | 评估 |
|---|---|
| **架构形态** | 静态站 + 第三方支付 |
| **服务端能力** | **仍然需要**（用户系统、订单管理） |
| **国内访问速度** | 主站 GitHub 慢 |
| **成本** | 第三方收取 1-2% 手续费 |
| **合规** | 第三方有牌照，自己不用办 |
| **扩展性** | 受限（被第三方绑定） |
| **风险** | 第三方平台稳定性、长期费率风险 |

**关键洞察**：第三方支付只解决"支付"环节，**用户系统、订单管理、订阅状态**依然需要服务端。

**适合**：不愿办支付牌照 / 量小不想投入 / 接受长期成本

---

### 方案 D · 推迟付费（纯静态 MVP）

**做法**：先把付费功能暂缓，只做"免费版 + 单文件下载 + 客户端 AI"。

| 维度 | 评估 |
|---|---|
| **架构形态** | 完全静态（GitHub Pages 够用） |
| **变现** | 0 收入但快速上线 |
| **用户系统** | 不需要（用设备 ID 区分） |
| **扩展性** | 受限 |
| **风险** | 商业化推迟，竞争对手抢位 |

**适合**：先验证产品 / 0 成本试水 / 接受推迟变现

## 4. 推荐方案（主理人判定）

### 4.1 岳上线的判定：**方案 B 拆分部署**

**理由**：
1. **国内访问速度**：主站慢没关系，工具本身是"下载后本地用"，访问慢的只是介绍页（10% 体验）
2. **数据合规**：用户数据 + 订单数据全在 BFF 国内云，符合《个人信息保护法》
3. **扩展性**：BFF 可独立扩展，未来加企业版/开放 API 不影响主站
4. **成本**：主站免费 + BFF 按量付费（MVP 阶段月成本 < ¥30）
5. **保留 GitHub Pages 优势**：开源、版本控制、PR/Issue 协作

### 4.2 推荐架构（详细）

```
┌────────────────────────────────────────────────────────┐
│ 主站：GitHub Pages                                     │
│ ┌──────────────────────────────────────────────────┐   │
│ │ 落地页 / 功能介绍 / 架构展示 / 下载页 / 隐私条款   │   │
│ │ 工具本体（index.html 单文件）                       │   │
│ │ AI 增强（用户自带 key，前端直调）                   │   │
│ │ 联系表单（Formspree.io 嵌入）                       │   │
│ └──────────────────────────────────────────────────┘   │
└────────────────────────┬───────────────────────────────┘
                         │ HTTPS API
                         │ CORS 白名单
                         ▼
┌────────────────────────────────────────────────────────┐
│ BFF：腾讯云 EdgeOne Pages（推荐）/ CloudBase            │
│ ┌──────────────────────────────────────────────────┐   │
│ │ Edge Functions：                                   │   │
│ │   POST /api/auth/register      注册               │   │
│ │   POST /api/auth/login         登录               │   │
│ │   GET  /api/auth/me            当前用户            │   │
│ │   POST /api/payment/wxpay      微信支付下单         │   │
│ │   POST /api/payment/callback   微信回调（验签）    │   │
│ │   GET  /api/subscription/me    订阅状态            │   │
│ │   POST /api/sync/upload        数据上传            │   │
│ │   GET  /api/sync/download      数据下载            │   │
│ │   GET  /api/usage/ai-quota     AI 配额查询         │   │
│ └──────────────────────────────────────────────────┘   │
│ ┌──────────────────────────────────────────────────┐   │
│ │ 数据库：CloudBase NoSQL 集合                       │   │
│ │   users: {_id, email, password_hash, createdAt}   │   │
│ │   subscriptions: {userId, plan, status, expiresAt}│   │
│ │   orders: {userId, planId, amount, status, txId}  │   │
│ │   ai_usage: {userId, month, count, lastCallAt}    │   │
│ └──────────────────────────────────────────────────┘   │
└────────────────────────────────────────────────────────┘
```

### 4.3 关键设计原则

| 原则 | 体现 |
|---|---|
| **数据最小化** | BFF 只存"鉴权/订单/订阅"4 张表；用户联系人数据**仍在本地** |
| **本地优先** | 工具离线可用，只有"多端同步"才需联网 |
| **渐进式上线** | D 方案（纯静态）→ B 方案（加 BFF）→ A 方案（视情况） |
| **优雅降级** | BFF 故障时，主站仍可访问、工具仍可用、AI 仍能调（带本地 key） |

### 4.4 上线策略（推荐渐进式）

| 阶段 | 范围 | 部署 |
|---|---|---|
| **第 1 步** | 工具落地页 + 工具本体 + AI（带 key） + 联系表单 | **仅 GitHub Pages**（纯静态） |
| **第 2 步** | + 用户注册/登录 + 数据云端备份 | + EdgeOne Pages BFF |
| **第 3 步** | + 14 天试用 + AI 配额限制 | BFF 扩展 |
| **第 4 步** | + 微信支付 + 订阅管理 | BFF 扩展 |
| **第 5 步** | + 多端实时同步 | BFF 优化 + WebSocket |

> **关键好处**：每一步都是可上线状态，可以边开发边收用户，不用等全部做完。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **微信支付申请驳回** | 变现推迟 | 推迟到 v1.5，先跑 MVP 收集用户 |
| **EdgeOne Pages Edge Functions 限制** | BFF 功能受限 | 提前验证 Function 能力边界，准备 CloudBase 备选 |
| **跨域 CORS 问题** | API 调用失败 | BFF 显式配置 CORS 白名单（主站域名） |
| **数据合规审查** | 国内运营受阻 | BFF 全量国内云、不出境；隐私政策明确 |
| **GitHub Pages 国内访问慢** | 落地页体验差 | CDN 镜像 / 国内备案后迁回国内 |
| **多端同步冲突** | 数据丢失 | MVP 阶段"最后写入获胜"；v2.0 用 CRDT |
